❓ What exactly is Weave and how would you explain it to a non-technical stakeholder?
Weave is IBM's agentic AI lifecycle platform — a factory that converts plain English business requirements into fully deployed, production-ready AI agents automatically. Instead of engineers spending months building agents from scratch, Weave auto-generates the Task Plan, agents, tools, and deployment in minutes.
❓ What was the hardest engineering challenge in building Weave?
The hardest challenge was designing the conditional routing engine — making the system decide at runtime which agent handles which task based on context. Getting the DAG generation to produce correct decision logic from ambiguous natural language requirements required extensive prompt engineering and validation loops.
❓ How does the MCP (Model Context Protocol) connector work? What did you build there?
MCP provides a standardised interface for agents to call external tools. I built 60+ connectors (Salesforce, SAP, ServiceNow, Workday) by transpiling their OpenAPI specs into MCP-compatible tool definitions. Each connector handles auth (OAuth2/SAML), rate limiting, error handling, and response normalisation automatically.
❓ Walk me through how Weave goes from a plain English requirement to a deployed agent.
Step 1: LLM parses the requirement into a structured task plan with decision nodes. Step 2: For each node, Weave generates a specialised agent (with role, goal, tools). Step 3: Tools are auto-created from OpenAPI specs. Step 4: A DAG wires the agents with conditional routing. Step 5: One-click deploys to IBM Watsonx Orchestrate with validation.
❓ How did you achieve 99.9% uptime at 10M+ daily API calls?
Through multi-region deployment on IBM Cloud OpenShift + Kubernetes with auto-scaling. Redis handles session state and caching. OpenTelemetry provides distributed tracing so we catch issues before they cascade. Circuit breakers on every MCP connector prevent downstream failures from taking down the whole system.
❓ What's the difference between Weave and LangChain / LangGraph? Why not just use those?
LangChain/LangGraph are great frameworks for building agents in code. Weave is a no-code/low-code platform on top — it uses LangGraph internally for orchestration but adds an enterprise layer: auto-generation from natural language, 60+ pre-built connectors, OAuth2/SAML security, one-click deployment, and governance integration with watsonx.governance.
❓ What happens when an agent fails mid-workflow? How do you handle error recovery?
Weave implements checkpoint-based recovery. Every agent action is logged to a durable state store (Redis). If an agent fails, the workflow can resume from the last checkpoint rather than restarting. For critical failures, we have fallback routing — the DAG has alternate paths. Human-in-the-loop escalation is triggered when confidence drops below threshold.
❓ How do you prevent agents from going rogue or producing hallucinated tool calls?
Three layers: (1) Tool schemas are strictly validated — agents can only call tools with the exact signature defined in the MCP spec. (2) Output guardrails check every agent response before it's routed to the next step. (3) The DAG structure itself limits what an agent can do — it can't call tools outside its defined scope. We also log everything for audit via watsonx.governance.
❓ The project went from concept to production in 14 months. What corners were cut and what would you do differently?
Honest answer: we under-invested in the developer portal and documentation early on. The first 6 months were pure platform building, and we added SDK docs and tutorials late. I'd front-load developer experience investment — a platform is only as good as how quickly others can build on it. We also added monitoring (OpenTelemetry) later than ideal; I'd instrument from day one next time.

❓ Why does AI governance matter? Can't you just trust your models?
Models drift over time — the data distribution changes, and a model trained 6 months ago may be making biased or incorrect decisions today with no visible warning signs. In regulated industries (banking, healthcare), a wrong model decision can mean regulatory fines or patient harm. Governance gives you real-time visibility, audit trails, and the ability to prove your AI is fair and compliant.
❓ What is an AI FactSheet and why did you introduce it?
An AI FactSheet is a machine-readable "birth certificate" for every deployed model — it records who trained it, on what data, with what hyperparameters, what bias tests were run, and what performance it had at deployment. Regulators under EU AI Act and ISO 42001 are starting to require this. It also means when a model makes a bad decision, you can trace back exactly what happened.
❓ How does IBM OpenScale detect drift in production?
OpenScale monitors two types of drift: data drift (input distribution shifts from training data, measured by Population Stability Index and KL divergence) and concept drift (model accuracy degrades, detected by comparing prediction distributions over time). When drift exceeds a threshold, it triggers automated retraining via the pipeline and alerts the governance dashboard.
❓ How did you map 200+ regulatory frameworks in watsonx.governance?
We built a policy-to-metric mapping layer in IBM OpenPages. Each regulatory framework (EU AI Act, NIST AI RMF, ISO 42001, GDPR, etc.) was decomposed into measurable controls. Each control was mapped to a model metric (fairness score, drift rate, data lineage completeness). The Governance Graph links model → metric → control → regulation — so you can query "which models are at risk for EU AI Act Article 10?"
❓ What is the difference between fairness, drift, and hallucination monitoring?
Fairness: Does the model produce different outcomes for different demographic groups (gender, race)? Measured by demographic parity, equal opportunity. Drift: Has the model's performance degraded over time due to changing data? Measured by PSI, KL divergence. Hallucination: Is the model generating false or fabricated information? Measured by factuality scores, citation verification, and groundedness checks.
❓ A model passes all governance checks but is still producing bad business outcomes. How?
Governance checks what you measure, not what you don't. A model can be statistically fair and non-drifting but still optimising for the wrong business objective. This is why we added business KPI tracking alongside model metrics — pairing model performance with downstream business outcomes (conversion rate, revenue impact). The model might be technically healthy but solving the wrong problem.
❓ How do you govern models across multi-cloud — IBM, AWS SageMaker, Azure ML simultaneously?
We use watsonx.governance as the central control plane. Each cloud has an agent that pushes model metadata (metrics, lineage, predictions) back to the governance layer via standardised connectors. IBM models are native; SageMaker and Azure ML use SDK integrations that pull model cards and push monitoring data. The Governance Graph normalises everything into a unified view regardless of cloud origin.

❓ Why use an SLM instead of a large LLM for banking? What's the trade-off?
An SLM (Small Language Model) fine-tuned on banking data beats a general LLM on domain-specific tasks for three reasons: (1) It's much cheaper to run — 10-100x lower inference cost. (2) It's faster — lower latency per query. (3) It's more precise — it only knows banking, so it doesn't hallucinate outside-domain answers. The trade-off: it can't handle novel, out-of-scope queries. That's fine for routine banking ops.
❓ How did you validate that AskFin was actually better than the large LLM baseline?
We ran a structured benchmark across 3 dimensions: quality (human eval on 500 test queries — accuracy, policy compliance, conciseness), latency (P50/P95 response times), and cost (tokens/query × price/token). AskFin matched or exceeded LLM quality on banking-specific queries at ~15% of the cost and 3x lower latency. We presented this as a quality-cost Pareto frontier to the bank's leadership.
❓ What is LoRA and why did you use it for fine-tuning instead of full fine-tuning?
LoRA (Low-Rank Adaptation) freezes the base model weights and adds small trainable matrices to the attention layers. This means we're only training ~1% of the parameters vs full fine-tuning. Benefits: 10x cheaper to train, no catastrophic forgetting of base knowledge, can be swapped in/out without reloading the base model. For a bank's budget, LoRA makes domain adaptation economically viable.
❓ What does the classification head do vs the generation head?
The classification head is a lightweight linear layer on top of the encoder that routes the query to a category (loan, KYC, account, compliance, ops). This is fast — it's just a softmax over 5-10 classes. The generation head is the autoregressive decoder that produces the actual response text, conditioned on the category. Splitting them lets us apply different quality gates per category.
❓ What if the SLM encounters a question it wasn't trained on? How do you handle OOD queries?
We added an out-of-distribution (OOD) detector — a separate classifier that measures query similarity to the training distribution. If confidence is below threshold, AskFin escalates to a human agent rather than generating a potentially wrong answer. In a bank, a confident wrong answer is far worse than admitting uncertainty. We also log OOD queries to continuously expand the training corpus.
❓ How do you ensure the model stays compliant as bank policies change?
We built a drift detection loop — every month, we run the model against a holdout of recent customer queries. If accuracy drops or new query patterns emerge, it triggers a LoRA re-fine-tuning job on the updated policy corpus. The whole pipeline (data update → fine-tune → eval → deploy) is automated via CI/CD, so policy changes propagate to the model within days, not months.

Business / Project Technical Deep-Dive Tricky / Gotcha
❓ What is RAG and why did you need it for banking documents?
RAG (Retrieval-Augmented Generation) means the LLM doesn't answer from memory — it first retrieves relevant chunks from your document library, then generates an answer grounded in those chunks. In banking, you can't let the LLM guess from training data. Every answer must come from the bank's actual policies and agreements. RAG provides that grounding + source citation.
❓ What's the business case for a 35% improvement in document processing efficiency?
NatWest processes thousands of documents per month — loan reviews, compliance checks, policy Q&A for staff. Each manual lookup took 15-45 minutes. AskBank cuts that to under 2 minutes. Across hundreds of staff doing dozens of lookups per day, that's thousands of hours saved per month, faster customer response times, and fewer errors from fatigued human reading.
❓ Why Hybrid RAG? Why not just use semantic search alone?
Semantic search (dense vectors) is great at capturing meaning and intent — "penalty for early repayment" finds clauses about early repayment fees even if the exact words differ. But it misses exact matches — clause numbers, product codes, regulatory IDs. BM25 keyword search catches those exactly. Hybrid combines both: semantic for meaning, keyword for precision. Neither alone covers all banking query types.
❓ Walk me through the Fusion + Re-ranking step.
After both retrievers return their top-k chunks, we use Reciprocal Rank Fusion (RRF) to merge the two ranked lists into one. Then a cross-encoder re-ranker (a BERT-style model) scores each candidate chunk against the query for relevance. Cross-encoders are more accurate than bi-encoders because they see the query and document together. The top N chunks after re-ranking go to the LLM.
❓ How do you handle very long banking documents that exceed the LLM context window?
Three strategies: (1) Hierarchical chunking — split at semantic boundaries (sections, clauses) not arbitrary token counts. (2) Metadata tagging — each chunk carries document name, section, page number so the retriever can do section-level filtering. (3) Map-reduce for summaries — for full document summarisation, we summarise each chunk then summarise the summaries. This gives complete coverage without truncation.
❓ What if the retriever returns the wrong chunk and the LLM answers confidently from it?
This is the "retrieval failure" problem. We mitigate with: (1) Confidence scoring — if the top retrieved chunk has low similarity to the query, we flag the response as low-confidence. (2) Faithfulness checks — we verify that the generated answer is actually supported by the retrieved chunks, not hallucinated. (3) Source display — showing users the cited chunk lets them verify. In banking, users are trained to always check the citation.
❓ How do you keep the vector index up to date as documents are updated?
We implemented incremental indexing — document change events trigger a re-embedding pipeline that: detects changed/added chunks, re-embeds only those chunks, updates the vector store with upserts. Deleted documents trigger chunk deletion. We also version documents so we can answer "based on the policy as of date X" — important for legal disputes where the document version matters.

(3) Early stakeholder alignment — we ran architecture review sessions in week 1 rather than presenting a finished design for approval, eliminating rework cycles.
❓ Why Azure Databricks for transformation? Why not Azure Data Factory alone?
ADF is great for orchestration and simple copy/move operations. But complex transformations — joins across large datasets, ML feature engineering, data quality logic — need distributed compute that ADF can't provide. Databricks with PySpark runs those transformations at scale. The pattern is: ADF triggers and orchestrates, Databricks executes the heavy computation. They complement each other.
❓ How do you ensure the architecture you design can handle future AI/ML workloads?
We designed with "AI readiness" as a first-class concern: (1) Delta Lake format for the data lakehouse — supports time travel, schema evolution, and direct integration with Azure ML. (2) Metadata catalog (Azure Purview) — every dataset is catalogued so ML teams can discover and understand data lineage. (3) Feature store pattern — computed features are stored and reusable across ML models. (4) Separate raw/curated/gold zones — raw data is never overwritten.

❓ What is a waste classification code and why is it a regulatory requirement?
The US EPA requires every hazardous waste stream to be assigned a specific code (D001-D043 for characteristic wastes, F/K/P/U codes for listed wastes). The code determines: how the waste must be stored, transported, treated, and disposed of. Wrong code = wrong disposal = federal EPA violation. Fines can reach $70,000 per day per violation. Getting it right every time is not optional.
❓ How did you collect the training data? What features did you use?
Training data came from historical waste manifests at Clean Harbors — physical property measurements recorded at the time of collection. Features: pH, flash point (ignitability), corrosivity (pH extremes), reactivity indicators, ignitability test results, colour, viscosity, specific gravity, halogen content, and chemical composition flags. Labels were the EPA waste codes assigned by the compliance team. ~30+ features total.
❓ Why XGBoost? Why not a neural network for this?
XGBoost was the right choice here for three reasons: (1) Tabular data with 30 features — neural networks don't outperform gradient boosting on tabular data at this scale. (2) Interpretability — compliance officers needed to understand why the model chose a code, and SHAP values on XGBoost are reliable and auditable. (3) Training data volume — we had thousands of records, not millions. XGBoost generalises better with limited data.
❓ What is SMOTE and why was class imbalance a problem here?
SMOTE (Synthetic Minority Over-sampling Technique) creates synthetic training examples for underrepresented classes by interpolating between existing minority samples. The class imbalance problem: most waste at Clean Harbors is non-hazardous or falls into common categories. Rare but critical hazardous codes (e.g., reactive wastes, acutely hazardous P-codes) had very few training examples. Without SMOTE, the model would predict common classes always and miss the dangerous rare ones.
❓ How did you implement drift detection and automated retraining?
Azure Data Factory monitored two drift signals: (1) Data drift — PSI (Population Stability Index) comparing incoming waste property distributions against training baseline. (2) Performance drift — monthly holdout evaluation against recently-labelled examples. If PSI > 0.2 or accuracy drops > 3%, ADF triggers an Azure ML pipeline that retrains on the updated dataset, runs validation, and promotes the new model if it passes quality gates.
❓ The model achieves 92% accuracy. What happens in the 8% of cases it gets wrong?
Great question — the answer defines how we designed the system. Mis-classification in this domain is not symmetric: misclassifying hazardous as non-hazardous is far worse than the reverse. So we built an asymmetric confidence threshold — the model only auto-classifies when confidence > 95%. Below that threshold, it flags for human review. This gives us near-100% precision on auto-classified cases while sending uncertain cases to experts. The 8% reflects total accuracy including the uncertain cases.
❓ How do you explain the model's decision to a compliance officer who isn't technical?
We used SHAP (SHapley Additive exPlanations) to generate natural-language explanations. For each classification, the officer sees: "This waste was classified as D001 (Ignitable) primarily because flash point = 42°C (below 60°C threshold) and it is a liquid." The SHAP values are translated into plain English feature contributions, ranked by importance. Compliance officers can verify the model's reasoning against the EPA regulatory criteria directly.

Business / Project Technical Deep-Dive Tricky / Gotcha
❓ How does a company lose $750K to invoice errors? Walk me through a real example.
Example: A cleanup job takes 8 hours, 3 trucks, 5 workers. The actual invoice is generated from a billing system that pulls hours from one system, truck count from another, and applies rates from a contract table. If the contract rate expired and the system defaulted to a higher rate, or if overtime hours were double-counted, or if a truck that left early was billed for the full day — each error is small but across thousands of jobs per year, it compounds. $750K is a conservative estimate.
❓ Why couldn't a rule-based system catch these errors instead of ML?
Rule-based systems catch known error patterns. ML catches unknown ones. A rule like "flag if hours > 12" works, but the errors were subtle combinations — correct hours but wrong contract tier, or normal hours/trucks but anomalous for that specific customer's historical pattern. ML learns the expected invoice amount from the joint distribution of all 47 features and flags deviations from that learned expectation. Rules can't capture that multi-dimensional interaction.
❓ What does the regression model actually predict? What is the target variable?
The target variable is the expected invoice total in dollars. The model is trained on historical invoices where the "correct" amount was verified (post-audit, post-dispute-resolution records). Given the 47 input features (hours, truck count, worker count, service codes, contract tier, customer type, job type, seasonal flag, etc.), the model predicts: "This job should have been invoiced at $X." Then we compute: flagged_gap = |actual_invoice - predicted_invoice|. If flagged_gap > threshold, it's sent for review.
❓ How did you choose the anomaly flagging threshold?
We used a precision-recall curve analysis. We plotted precision and recall at different threshold values on the validation set (invoices with known errors). We selected the threshold that maximised F-beta score with beta=0.5 — weighting precision higher than recall, because in this domain, false positives (flagging correct invoices) waste auditor time, while false negatives (missing errors) cost money. The optimal threshold balanced a ~95% precision at a recall that still caught the material errors.
❓ How does automated retraining work when billing patterns change?
Billing patterns shift with contract renewals, seasonal rate changes, and new service categories. Azure Data Factory monitors the prediction residual distribution monthly. If the mean residual or its variance shifts significantly (measured by t-test and F-test against a baseline window), it triggers a retraining job. The pipeline: pull last 18 months of verified invoices → feature engineering → retrain → evaluate on holdout → A/B test new vs old model → promote if improved.
❓ How do you handle the case where the model is wrong and flags a correct invoice?
The Power BI dashboard shows the model's confidence score alongside each flag and the top contributing features (SHAP). Auditors see: "Flagged because truck count (3) is higher than expected (1.8) for this job type." If the auditor confirms it's correct (e.g., the job genuinely needed 3 trucks), they mark it as reviewed. This becomes a training signal — the model gets periodic feedback corrections, improving its calibration on legitimate edge cases over time.
❓ Could this system be gamed by a dishonest billing team who knows how it works?
Yes — this is a real adversarial ML concern. Our mitigations: (1) The model's exact thresholds are not exposed to billing staff — they only see that flags exist, not the model logic. (2) The model is retrained on evolving data, so a pattern that evades it today gets caught after the next training cycle. (3) We added a second, independent statistical layer (Z-score on peer-group invoices) that doesn't depend on the ML model. Gaming one layer doesn't defeat both.

⚡ Quick-Fire Technical Questions
❓ What is the difference between precision and recall? When does each matter more?
Precision = of all the times I said positive, how often was I right? Recall = of all actual positives, how many did I catch? Precision matters more when false positives are costly (spam filter — you don't want legitimate emails flagged). Recall matters more when false negatives are costly (cancer screening — you don't want to miss a case). In WCC, I weighted precision higher for auto-classification (don't want confident wrong EPA codes). In Invoice Audit, recall matters more (don't miss revenue leakage).
❓ What is gradient boosting and why does it outperform random forests on tabular data?
Both are ensembles of decision trees. Random Forest builds trees independently in parallel (bagging — reduces variance). Gradient Boosting builds trees sequentially — each tree corrects the errors of the previous one (boosting — reduces bias). GBM typically outperforms RF on tabular data because it can model complex interactions with fewer trees. XGBoost adds L1/L2 regularisation and better handling of missing values. RF is better when you want less tuning and more robustness to outliers.
❓ Explain attention mechanism in transformers in simple terms.
Attention lets every word in a sentence look at every other word and decide how much to focus on it when building its representation. For "The bank on the river bank" — the model learns that "bank" (first) should attend heavily to "river" to understand it means a riverbank, not a financial bank. Multi-head attention runs this process in parallel multiple times with different "perspectives," capturing different types of relationships simultaneously.
❓ What is the difference between fine-tuning and RAG? When would you use each?
Fine-tuning bakes knowledge into the model weights — the model "memorises" the domain. Good for: changing the model's style/tone/behaviour, teaching it domain-specific language patterns. Bad for: keeping knowledge current (retraining is expensive), source citation. RAG keeps knowledge external, retrieved at inference time. Good for: up-to-date information, source traceability, large document corpora. Bad for: latency-sensitive applications, when you need the model's own reasoning to change. In practice: fine-tune for behaviour, RAG for knowledge.
❓ What is data drift vs concept drift? Give a banking example.
Data drift: the distribution of input features changes. Example: post-COVID, customers' transaction patterns shifted dramatically — average balance, spending categories all changed. The model's inputs look different from training. Concept drift: the relationship between inputs and the correct output changes. Example: a customer behavior that used to indicate low fraud risk (regular small transactions) is now being exploited as a fraud pattern. Same inputs, different correct label. Data drift you detect with statistical tests on features. Concept drift requires monitoring model performance on labelled recent data.
❓ What is the vanishing gradient problem and how is it solved?
In deep networks trained with backpropagation, gradients are multiplied through many layers. If they're small (<1), they shrink exponentially toward earlier layers — those layers learn very slowly or not at all. Solutions: (1) Residual connections (ResNets) — add a skip connection so gradients can flow directly. (2) Batch normalisation — normalises layer inputs, keeping gradients in a stable range. (3) Better activations — ReLU instead of sigmoid, which saturates at extremes. (4) Gradient clipping — caps gradients at a max value for RNNs.
